# 《AI Engineering》Chip Huyen (2025) — AI PM 可执行框架

## 核心框架

### 1. EDD（Evaluation-Driven Development）评测驱动开发

传统 TDD 的 AI 版：**先定义你怎么评判好坏，再开始构建**。

四大评测维度：
| 维度 | 核心问题 | PM 动作 |
|------|----------|---------|
| 领域能力 | 模型理解这个垂直领域吗？ | 构建你业务场景的多选题评测集 |
| 生成能力 | 输出事实准确吗？内部一致吗？ | 区分局部一致性（单次输出自洽）vs 全局一致性（与外部事实对齐） |
| 指令遵循 | 能按规定格式/长度/语气输出吗？ | 先排除是 prompt 写得差还是模型不行（指令-性能悖论） |
| 成本与延迟 | 单次调用多少钱、多快？ | 用帕累托优化做多目标权衡，不做单一最优 |

**PM 一句话**：上线前没有可量化的评测标准 = 永远在"调 prompt"里打转。

### 2. 适应决策阶梯：Prompt → RAG → Fine-tune

每种方案解决不同的问题，**从最便宜的开始，够用了就停**。

```
Prompt Engineering（零成本，分钟级迭代）
    ↓ 如果瓶颈是"模型缺少信息"
RAG（中成本，知识外挂，可更新无需重训）
    ↓ 如果瓶颈是"模型缺少行为模式"
Fine-tuning（高成本，永久改变权重）
```

关键诊断问题：**失败是信息问题还是行为问题？**
- 信息问题（缺私有数据、事件在训练截止后）→ RAG
- 行为问题（格式不对、语气不对、系统性错误模式）→ Fine-tune
- **大部分团队在 Prompt + RAG 就能覆盖 80%+ 场景，过早 Fine-tune 是常见错误。**

### 3. AI 应用构建四阶段

| 阶段 | 目标 | PM 关卡 |
|------|------|---------|
| 原型 | 证明可行性 | 设定最低可用质量阈值，防止 demo 即满足 |
| 上线 | 真实用户使用 | 定义失败模式，建立回退机制 |
| 迭代 | 基于反馈持续优化 | 从 0→80 分很快（1 个月），80→95 分极慢（可能 4 个月+） |
| 维护 | 对抗退化 | 模型弃用、能力漂移、用户期望变化都需要主动管理 |

**80/20 陷阱**：做一个 80% 的 demo 只需几周，但把最后 20% 做成生产级可靠系统，成本可能等于前面全部投入。

## 行动清单

### 立项前必答三问
1. **我准备怎么度量这个功能的好坏？**（不能说"用了就知道"）
2. **上线后最坏会错成什么样？**（定义失败边界，建兜底策略）
3. **上线后谁为结果负责？**（必须在 go-live 前指定 owner，不能是"团队共同负责"）

### 评测体系搭建四步
1. 做 50–200 条 Golden Dataset（真实场景输入+期望输出）
2. 写评分量表（每个分数配具体案例，人工校验无歧义）
3. 用 AI-as-Judge 做自动评测（注意三个偏差：自我偏爱 +10%、位置偏爱首个回答、冗长偏爱）
4. 把评测指标映射到业务指标（80% 事实准确对业务意味着什么？）

### 成本控制节奏
- 初期：用前沿模型做所有调用，先验证价值
- 中期：引入模型路由——简单问题走小模型，复杂问题走大模型
- 长期：对高频固定 pattern 做缓存，对明确行为模式做 Fine-tune 压缩系统 prompt 成本

## 决策工具

### Fine-tune 是否值得的判定矩阵

| 条件 | Fine-tune | 不 Fine-tune |
|------|-----------|-------------|
| 日调用量 < 1000 次 | ❌ 投资回报不够 | ✅ Prompt+RAG 足够 |
| 日调用量 > 100 万次 | ✅ 省 API 费 | ❌ 边际成本太高 |
| 需要 99.9% 固定 schema 输出 | ✅ Prompt 有天花板 | — |
| 知识频繁更新（周级） | ❌ 每更新需重训 | ✅ RAG 只重建索引 |
| 有 500+ 高质量标注样本 | ✅ 可以动手 | — |
| 样本不到 100 条 | ❌ 质量 > 数量 | — |

### 代理（Agent）风险公式
代理可靠性 = 单步可靠率 ^ 步数。如果每步 95% 可靠，10 步后只剩 60%。
**策略**：给不可逆操作（写数据库、发消息、扣款）加确定性门控，不让模型直接执行。

### 壁垒三要素
技术（基础模型正在商品化）→ 数据（最可行的创业壁垒）→ 渠道（大公司优势）
**PM 策略**：尽快上线收集使用数据，建立数据飞轮。

## 常见错误

1. **跳过 Prompt 直接 Fine-tune**：大部分"模型不行"其实是 prompt 写得不够好。先花 3 天认真写 system prompt + 6 个 few-shot 示例。
2. **没有评测就开始迭代**："调了 prompt 感觉好多了"不是工程判断。每次改动必须跑同一套评测集看数字。
3. **用信息问题当行为问题修**：模型不知道公司最新定价 → 该加 RAG 而非 Fine-tune。
4. **把 demo 当成产品**：80% demo 到 95% 生产级的差距被严重低估，schedule 要预留 4 倍时间。
5. **AI Judge 不自检偏差**：用同一个模型的输出去评测自己，会给自己打高 10% 分。
6. **代理没有硬门控**：让 Agent 直接发邮件/扣款而不加确定性校验，是生产事故头号来源。

## 应用边界

### 适用场景
- 构建基于基础模型的应用（不是从零训模型）
- 需要在 Prompt / RAG / Fine-tune 之间做技术方案选择
- 搭建 AI 产品评测体系和 CI/CD pipeline
- 从原型走向生产级的系统化工程

### 不适用场景
- 从零训练专有模型的研究课题
- 纯传统 ML（分类/回归/推荐）—— 去看同作者的《Designing Machine Learning Systems》
- 已有成熟评测体系、只需要调优具体实现细节的团队
