# Marty Cagan 产品心智模型

## 心智模型

### 1. 四大风险框架（The Four Big Risks）

任何产品想法在投入工程之前，必须同时降低四类风险——缺一不可：

| 风险 | 核心问题 | 负责人 | 验证手段 |
|------|---------|--------|---------|
| **价值风险** | 客户会不会买/用户会不会用？ | PM | 用户访谈、定性价值测试（要求用户付出时间/金钱/声誉） |
| **可用性风险** | 用户能不能搞清楚怎么用？ | 设计师 | 原型测试（5个目标用户，观察3/5是否卡在同一步） |
| **可行性风险** | 工程团队能否在现有技术/时间下构建？ | 技术负责人 | 技术spike、可行性验证 |
| **商业可行性风险** | 方案是否适配销售的渠道/合规/财务/品牌？ | PM | 利益相关方评审 |

**PM 对价值和可行性负责，对产品结果负总责。** 大多数团队只检查可行性，轻视价值，忽视商业可行性——这是系统性失败根源。

### 2. 赋能团队 vs 功能团队（Empowered vs Feature Teams）

| 维度 | 功能团队 | 赋能团队 |
|------|---------|---------|
| 输入 | 被给功能路线图 | 被给问题和业务结果 |
| PM角色 | 项目经理/工单管理员 | 产品策略师/探索领导者 |
| 衡量 | 产出（按时发布功能） | 结果（业务/客户指标） |
| 自主权 | 低——执行指令 | 高——在护栏内选择方案 |
| 探索 | 几乎没有 | 持续双轨进行 |
| 心态 | 雇佣兵（build what they're told） | 传教士（true believers in the vision） |

**赋能 = 人才能力 + 高管信任，两者缺一即退化为功能工厂。** 赋能不是放任，是给问题、给上下文、给自主权、要结果。

### 3. 双轨并行（Discovery ↔ Delivery）

产品探索不是交付前的阶段，而是与交付持续并行的实践：
- **探索**：快速、廉价地分离好想法和坏想法——用原型而非幻灯片
- **交付**：构建生产级质量的产品
- 两条轨道始终同时运行，学习周期以天/周计，而非月/季
- **工程师必须在探索阶段参与**——他们是创新的最佳来源，而非交付工具

### 4. 结果导向 vs 产出导向

两个不便的真相：(1) 至少一半的想法不会奏效；(2) 即使有潜力的想法也需要多次迭代。因此：
- 路线图不应是功能+日期的承诺清单，而应是业务结果的目标
- 战略的本质是决定不做什么——聚焦1-2件能真正撬动杠杆的事
- "如果你有50个优先级项目，那不是聚焦，那需要一次干预"

### 5. AI 时代的产品判断

AI 使构建变容易，但使判断变关键：
- "工作不再是构建，而是思考。这是剩下的东西。"
- AI 能让你更快地构建错误的东西——速度不等于方向
- 原型周期从周压缩到小时，但PM的真实价值在于评估而非执行
- 四大风险框架在AI产品中更难：产品从确定性变为概率性，质量保证需要新方法
- PM角色在生成式AI时代更重要也更难，而非更不重要

## 判断决策

### 需求是否值得做——四问 gates

在投入工程前，逐项回答：
1. **价值证据**：你有来自真实用户的行为证据吗？（不是问卷/焦点小组，是原型测试+定性价值测试）
2. **可用性证据**：5个目标用户测试原型，3个以上能完成核心任务吗？
3. **可行性证据**：技术负责人确认在现有约束下可构建吗？
4. **商业可行性证据**：销售/法务/财务/品牌团队确认无阻断吗？

**任何一项证据不足 = 你有的是探索问题，不是交付决策。**

### 团队诊断——6个判断题

| 问题 | 赋能团队 | 功能团队 |
|------|---------|---------|
| 谁决定做什么？ | 团队基于探索和策略 | 利益相关方/领导 |
| 多久接触一次客户？ | 至少每周 | 很少/从不 |
| 路线图包含什么？ | 结果和待解决的问题 | 功能+交付日期 |
| 成功如何衡量？ | 客户和业务结果 | 按时发布功能 |
| 能否对利益相关方说不？ | 能，用证据 | 不能，请求变需求 |
| 工程师参与探索吗？ | 是，从第一天 | 不，只接需求 |

### 聚焦判断

- 如果你列了超过3个"最高优先级"，你没有聚焦
- 对路线图每个项目，写下它要达成的业务结果——如果换个方案能更好达成同样结果，团队是否被允许换？如果不能，你有的是功能承诺，不是战略

## 行动指引

### 产品探索 checklist

- [ ] 用原型而非幻灯片测试想法
- [ ] 每个重要想法用5个目标用户做原型测试
- [ ] 工程师参与客户访谈和原型测试（不只是接需求）
- [ ] 对价值风险，要求用户付出真实代价（时间/金钱/声誉）
- [ ] 先攻击最大风险——通常是价值风险和商业风险
- [ ] 探索与交付并行，不是串行
- [ ] 每两周至少发布一个验证过的增量

### 需求评审 gates

- [ ] PM能说出客户top 3问题（来自直接观察，不是二手报告）
- [ ] 四大风险各有具体证据，不是假设
- [ ] 定义的是最小可行产品——能达成目标的最小范围
- [ ] 有真实参考客户（付费、生产环境使用、愿意主动推荐）
- [ ] 团队能解释产品愿景和战略上下文

### AI 时代补充

- [ ] AI是助手不是决策者——优先级和判断仍由人负责
- [ ] 用AI加速探索（原型、分析、总结），但验证必须通过真实用户行为
- [ ] 警惕"用工件代替工作"——AI能快速生成PRD/路线图，但没有探索的工件只是猜测的包装
- [ ] 概率性产品需要新的质量保证方法
- [ ] 解决方案仍需比现有方案好10倍，而非加个AI贴牌

## 标志性提问

1. **"你给团队的是要解决的问题，还是要发布的功能？"**
2. **"你的路线图上如果换个方案能达成同样业务结果，团队被允许换吗？"**
3. **"你有多少个最高优先级？"**（超过3个=没有聚焦）
4. **"你最后一次和真实客户交谈是什么时候？"**
5. **"团队里谁是雇佣兵，谁是传教士？"**
6. **"你是在爱上问题，还是在爱上方案？"**
7. **"如果你不觉得第一个版本尴尬，你等了太久才获取用户反馈。"**
8. **"AI让你更快了——但你在更快地构建对的东西，还是更快地构建错的东西？"**

## 应用边界

### 适用场景
- 需要判断需求真伪和优先级时
- 评估产品团队组织模式（功能团队 vs 赋能团队）
- 设计产品探索流程和验证 gates
- 做产品战略和聚焦决策
- AI 产品需要评估四大风险（尤其概率性带来的新质量风险）
- 组织转型到 Product Operating Model

### 不适用场景
- 纯交付/外包团队（Cagan 明确说他不关心这类团队）
- 强监管/合同驱动的项目制环境（功能团队模式可能是合规要求）
- 早期阶段缺乏资深PM人才时——框架正确但无法落地，需要先建能力
- 销售驱动的企业级公司中，销售直接决定路线图时——需先解决高管对齐
- Cagan 框架产自前移动/前云时代，对现代 B2B SaaS/市场型业务的具体动态覆盖不完整，可补充 Shreyas Doshi 的 LNO 框架

### 关键提醒
框架被误用的最常见方式：公司采纳了敏捷词汇和产品仪式，但没有改变底层的信任、人才和高管行为——结果是"有更好流程剧院的功能工厂"。**赋能无法自下而上安装，必须高管先变。**
